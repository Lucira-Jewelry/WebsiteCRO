Sprint 1 — Unblock the funnel

this week · 5 tasks

Nothing here needs a redesign or a data migration. Ship these before touching anything else, because they change the numbers every later task is measured against.

T1

Convert the mobile checkout login modal to a bottom sheet

CriticalFrontend ~4 hours+₹4–6L / mo modelled

Desktop converts 4.2× better through the identical gate because the cart, total and step progress stay visible. Reproduce that context on mobile. This is the single best effort-to-impact ratio in the plan.

  1. Change the modal from full-viewport to a bottom sheet occupying ~60% of the viewport height.
  2. Keep the cart summary and the CART 1/3 step indicator visible above the sheet.
  3. Retitle from “Welcome to Lucira” to state the purpose — e.g. “Verify your number to continue to shipping”.
  4. Show the order total inside the sheet, so the user knows what they are logging in for.
  5. Give the close control a hit area of at least 44×44 px.
Acceptance test Run cro_funnel_walk at device: "mobile". The cart step must report blocking_overlay.coverage_pct < 60 and the cart total must still be readable in the screenshot. Compare against today's baseline of 100.
Update (4 Aug) Live-tested caratlane.com's mobile checkout: they also require phone/OTP login before payment (no guest checkout), confirmed by walking a real cart to "Place Order." That validates this task's direction — the fix was never "remove login," it's exactly this: present it as a step (bottom sheet, cart still visible), triggered at checkout commitment — not a full-screen takeover on first tap. CaratLane's own flow does this too: cart is fully open, login only appears at "Place Order," inside a visible Address→Gifting→Payment progression with the order total always in view. Treat their pattern as a second reference alongside Lucira's own desktop experience.

Sprint 2 — Remove the commitment barrier

next 2 weeks · 4 tasks

T2 is the largest single prize in the plan but needs real development and ideally a test harness. T14 is small but must ship alongside it, or you will have no way to measure whether T2 worked.

T2

REVISED 4 Aug — Move login to checkout commitment, not cart entry; guest checkout is no longer the ask

CriticalFrontend + backend ~2–3 days+₹8–12L / mo modelled pairs with T14
Correction (4 Aug) The original version of this task asked for guest checkout. A live competitive test on caratlane.com (a direct, larger jewellery competitor) found they also require phone/OTP login before payment, with no guest option — this is a category norm, not a Lucira-specific mistake, so guest checkout is no longer the recommended fix. Downgraded from "add a new checkout path" to "fix where and how login is triggered," which is a smaller, cheaper build. See T1's update for the full competitive detail.

A mandatory OTP appearing the instant "Proceed to Checkout" is tapped asks for commitment before the visitor has seen shipping cost or delivery date, and it hides the cart behind a full-screen takeover. CaratLane's pattern (and Lucira's own desktop pattern) keeps the cart open and only asks for login at the point of actually placing the order — as one step in a visible flow, not an interruption.

  1. Keep the login requirement — do not build a guest/anonymous-order path.
  2. Trigger the phone/OTP step only at genuine checkout commitment (equivalent to CaratLane's "Place Order"), not immediately on the cart's checkout button.
  3. Keep cart contents and total visible or collapsible throughout the login step — mirror T1's bottom-sheet approach rather than a full takeover.
  4. Add a visible progress indicator (Address/Shipping/Payment-style) so the login step reads as "step 1 of a flow," not a random wall.
Acceptance test cro_funnel_walk at device: "mobile": the login step must render with blocking_overlay.coverage_pct < 60 and the cart/order total still legible, matching T1's bar — this task is really T1's fix extended to the full checkout-commitment moment, not a separate guest path.
T14

Fire begin_checkout when checkout opens, not after OTP succeeds

CriticalFrontend + analytics ~2 hoursrequired to measure T1 & T2

GA4 records 144 mobile begin_checkout against 1,964 cart users. That 7.3% is partly a measurement artifact: the event currently fires after OTP verification, so everyone blocked by the wall is invisible. Without this fix you cannot distinguish “T1 worked” from “the event moved”.

  1. Fire begin_checkout on the checkout intent — the button click — not on successful auth.
  2. Add a separate event for OTP shown / OTP completed, so the gate's cost is measurable in its own right.
  3. Record the change date prominently; it creates a step change in the funnel that is not a behaviour change.
Acceptance test begin_checkout should rise sharply toward cart-page user count while purchases stay flat. That is the expected and correct outcome — annotate it so nobody later reads it as a conversion win.

How to verify anything actually worked

before / after protocol

Do not judge these changes on next-day conversion rate. Purchases run 2–3 per day, so a single day tells you nothing. Use the lab test for “did the change ship correctly” and the dashboard for “did behaviour move”.

The lab test — immediate, deterministic

Run the relevant cro_* tool before the change and again after. It answers “is the thing actually fixed”, in minutes, with no waiting for traffic.
